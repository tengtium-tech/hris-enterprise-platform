# backend/

.NET 9 modular monolith backend for the HRIS Enterprise Platform.

## Solution structure

* `Hris.sln` — the solution. `Directory.Build.props` sets solution-wide conventions: nullable reference types, implicit usings, file-scoped namespaces, and analyzers treated as build errors.
* `src/Api/` — the single deployable ASP.NET Core host. Currently exposes only `/health/live` and `/health/ready`; no business endpoints yet.
* `src/BuildingBlocks/Hris.SharedKernel/` — shared building blocks used by every framework and module: the `Result` pattern for error handling, strongly-typed IDs, and base `AggregateRoot`/`Entity`/`ValueObject` types.
* `src/BuildingBlocks/Hris.Application/` — shared Application-layer building blocks used by every framework and module: `ICommand`/`IQuery` MediatR markers, the `IUnitOfWork` abstraction, and the `ValidationBehavior`/`TransactionBehavior` MediatR pipeline behaviors, per `docs/02-architecture/03-application-architecture/application-pipeline.md`. Has no reference to Entity Framework Core or any other Infrastructure concern.
* `src/BuildingBlocks/Hris.Infrastructure/` — the one shared `HrisDbContext`, per `docs/02-architecture/05-data-architecture/dbcontext-design.md`'s "one application DbContext during the Modular Monolith phase." Discovers every framework's/module's own `IEntityTypeConfiguration` classes by assembly scanning rather than referencing them directly; implements `Hris.Application`'s `IUnitOfWork`.
* `src/BuildingBlocks/Hris.Foundation.*/` — the nine Core Kernel foundation frameworks: Configuration, Logging, Identity, Events, Authorization, Audit, Rules Engine, Validation, and Localization. All nine are complete: Domain layer (aggregates, value objects, domain events), Application layer, and Infrastructure layer. Two shapes coexist by design, not by omission — Logging and Validation Frameworks have no MediatR commands/queries or EF Core persistence of their own (neither describes a user-driven business command lifecycle, and Validation has no aggregate of its own to persist); each is a plain Application-layer service facade (`ILoggingService`, `IValidationService`) over a Domain-owned port its Infrastructure layer implements (`ILogSink` → Serilog, `IValidationResultTranslator` → the FluentValidation adapter). The other seven follow the standard CQRS-aggregate-command shape `ConfigurationSettingRepository` and its siblings establish.
* `src/Modules/` — empty by design. Business modules (organization, employee, payroll, and the rest) are added one at a time, each when its own development phase begins. See `src/Modules/README.md` for the intended build order.
* `tests/Hris.CriticalRequirements.Tests/` — one stub test per Critical Test Requirement (59 total), covering authorization, tenant isolation, audit trails, payroll correctness, workflow orchestration, and notification delivery. A test is unskipped only once the module or framework it exercises actually exists and the test genuinely exercises it.
* `tests/Hris.Infrastructure.IntegrationTests/` — real integration tests against a real, disposable PostgreSQL 16 instance via Testcontainers (never the EF Core InMemory provider, per `docs/09-testing/unit-and-integration-testing.md`'s own standing rule). Currently scoped to one class of risk: LINQ predicates that compare a converted Value Object, reach into an owned-type navigation, or translate a client-side collection into a SQL `IN` clause, across every repository in the Core Kernel using one of those shapes. Broader repository/command/query coverage is a separate, larger, tracked item (HEP-52), not this project's own scope.
* `Dockerfile`, `docker-compose.yml` — one backend image (multi-stage build, non-root runtime user); `docker-compose.yml` is for local Postgres/Redis only, not a deployment definition.
* `../.github/workflows/` — CI pipelines. Vulnerability scanning (Trivy) and container registry push (`ghcr.io`) are real, not placeholders. OpenAPI generation and deployment remain explicit placeholders until a Development hosting target is chosen.
* `../.editorconfig` — formatting rules only; nullable/implicit-usings/file-scoped-namespace enforcement lives in `Directory.Build.props`.

## Current status

Sprint 3 (Core Kernel) is complete. All nine foundation frameworks — Configuration, Logging, Identity, Events, Authorization, Audit, Rules Engine, Validation, Localization — have real Domain, Application, and Infrastructure layers, built in that bootstrap order (`IMPLEMENTATION-PLAN.md`'s own resolution of the nine-way dependency cycle among them). Each is registered in `Hris.Api`'s own `Program.cs`, in the same order, with each framework's own concretely-wired upstream dependencies documented inline there. No business module exists yet — the Core Kernel had to be complete first, since every module depends on it. Sprint 4 (Tenant, Extension, File Storage, Numbering, Search, Scheduling, Job Processing, Statutory Reference Data) is in progress: Tenant Framework is complete (Domain, Application, Infrastructure layers, plus its own unit test suite from day one rather than a future backfill), registered in `Program.cs` after the nine kernel frameworks; the remaining seven have no forced order among them, per `IMPLEMENTATION-PLAN.md`'s own resolution.

Every PR into this repository runs a real `dotnet build` (`-warnaserror`), `dotnet test`, and `dotnet format --verify-no-changes` in a real .NET environment — not merely parsed. `tests/Hris.Infrastructure.IntegrationTests/` adds real integration coverage against a real, disposable PostgreSQL 16 instance via Testcontainers, not the EF Core InMemory provider.

Two cross-cutting defects were found and fixed during Sprint 3, both the kind no unit test (which never constructs a real `HrisDbContext`) could have caught:

* **EF Core owned-type constructor-binding failures.** `HrisDbContext.Model` had never actually been built anywhere in this repository's history before Rules Engine's own PR needed to verify a nested-owned-collection mapping. Forcing that build for the first time surfaced that six aggregates across five frameworks (`ConfigurationSetting`, `UserAccount`, `OutboxEntry`, `RoleAssignment`, `RolePermissionGrant`, `RuleVersion`) pass an owned-type reference or collection straight through their own constructor, which EF Core's materialization convention cannot bind — plus one unrelated name-mismatch defect (`AuditRecord`'s constructor parameter was named `result`; the mapped property is `Outcome`). All seven are fixed: each affected aggregate gained a second, additive, EF-Core-only constructor omitting the unbindable parameter; `AuditRecord`'s parameter was renamed. `HrisDbContext.Model` now builds successfully end to end.
* **Value Object equality in LINQ predicates, and owned-navigation/`Contains` filters, against the real PostgreSQL provider.** Every `ValueObject` overloads `==` with a custom, component-wise operator rather than reference equality — reasonable grounds to doubt EF Core's Npgsql translator would accept that overload in a `Where` predicate rather than throwing "could not be translated," and no test had ever confirmed it against a real database. Seven repositories using this shape, plus the two related shapes (an owned-type navigation reached from a predicate, and a client-side collection translated into a SQL `IN` clause), are now confirmed correct against a real, disposable PostgreSQL 16 instance via Testcontainers — see `tests/Hris.Infrastructure.IntegrationTests/RepositoryQueryTranslationTests.cs` and each repository's own `VERIFIED` remarks. No repository code changed as a result of this one — every comparison was already correct as written.

## What hasn't been verified yet

* No EF Core migration has been generated yet for `HrisDbContext` — the first `dotnet ef migrations add` run is still unverified. `tests/Hris.Infrastructure.IntegrationTests/` sidesteps this today via `Database.EnsureCreatedAsync()` (schema built directly from the model, no migration files), which is fine for confirming query translation but is not a substitute for a real migration exercising `dotnet ef database update` against a real deployment path.
* The Development environment's own hosting target (cloud provider, VM, container platform) is still an open decision — CI's deployment stage stays a placeholder until it's made.
* Broader unit test coverage for the Sprint 3 Domain layer, beyond the 59 Critical Test Requirement stubs and the narrowly-scoped query-translation integration tests above, remains open (tracked separately, not blocking Sprint 4).

## Running locally

```
docker compose -f backend/docker-compose.yml up -d   # Postgres + Redis
dotnet user-secrets set "ConnectionStrings:HrisDatabase" "Host=localhost;Database=hris;Username=hris;Password=hris" --project backend/src/Api
dotnet run --project backend/src/Api
```

The connection string is required, not optional — `AddHrisInfrastructure` throws on startup if `ConnectionStrings:HrisDatabase` is missing, per module-registration.md's "fail startup loudly where a module's required configuration or dependency is absent" and environment-strategy.md's own rule that a connection string never lives in `appsettings.json`. `dotnet user-secrets` (not a checked-in file) is the right place for it locally; a real environment reads it from that environment's own secrets manager instead.

No EF Core migration exists yet, so the database itself has no schema even once the container is running — `dotnet ef migrations add InitialCreate --project backend/src/BuildingBlocks/Hris.Infrastructure --startup-project backend/src/Api` is the next real step, still unverified per "What hasn't been verified yet" above.

`GET http://localhost:8080/health/live` and `/health/ready` should both respond once the host starts; `/health/ready` now depends on the database connection (it will report unhealthy without one, by design). Nothing else is wired up yet.
